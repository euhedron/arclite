Description is a liability, not a virtue — every comment, note, or explanatory line must earn its existence against the real costs it imposes: it drifts out of sync with what it describes, it must be maintained, and the next reader (especially an agent) mistakes it for authority and propagates it. The default amount of description is therefore none, and the burden is on each line to justify why its absence would cause a concrete, likely error — not to justify its removal. Three cases make the default especially clear: a comment that restates what the code plainly says is pure noise; prose describing something *configurable* — meant to change — stamps a moving target with a fixed caption that is wrong the moment it moves; and prose describing machinery slated to be replaced invests maintenance in a corpse. Rationale that genuinely matters does not belong inline where it rots and hardens into false canon — it belongs in the specification (facets, items), stated once with provenance, citable, revisable. The failure mode compounds in two ways worth naming: the reflex to *trim* unjustified prose instead of *deleting* it (half-measuring, leaving a smaller version of the same liability), and the treatment of a label as fixed when it is merely the current choice — a thing called "audit" or "advisory" today is a configuration that may be renamed, so writing as though the name is canonical bakes in drift. The infection is self-replicating: noise authored confidently reads as intent, so the next agent preserves and extends it, and entropy accretes under the appearance of diligence. Flag description added or preserved where its absence would cause no concrete error — restatement of self-evident code, captions on configurable or soon-replaced machinery, decision-rationale narrated inline rather than placed in the specification, and any trimming of such prose where deletion was the correct move.
