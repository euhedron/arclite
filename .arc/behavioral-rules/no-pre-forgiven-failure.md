Never wrap a component the system owns in failure-tolerance before that failure has been observed. Let the unexpected raise, loud and immediate: a real failure gets fixed in the moment, with its exact error in hand, while the evidence is freshest — not absorbed by an accommodation that demotes it to a log line or swallows it so the defect keeps happening quietly. "Transient" is the smuggling word: a claim about a failure's cause and duration, made in advance, about a failure never yet seen — provenance-free, and it pre-forgives the real failure before it has even happened. Code shaped to expect its own failure also asserts, in its very structure, that the system's own writes fail sometimes — a statement with zero evidence behind it that manufactures distrust of one's own work. Failure-handling is a designed, visible feature, built for failure modes that have been observed or that the design names as expected operating conditions of things the system does not own — a remote API, a network, user input — never a reflex try/except around an owned step. Continue-despite-failure is legitimate only narrowly: the surrounding work genuinely outranks the failing part, the failure still surfaces at full volume, and the failing thing is outside the design's own guarantees; bare "keep things going" is the anti-pattern. The tell-words in a diff: "transient", "best-effort", "degrade gracefully", "just in case", "defensive" — and the cargo-culted distributed-systems posture (independent component failure, partial availability) inside a single local process whose components share one disk and one fate. (Sibling of the speculative-defensive-code rule, which rejects accommodating design-impossible states; this rejects pre-accommodating unobserved failures of owned components.) Flag failure-tolerance — a swallow, a soften, a continue — wrapped around an owned component with no observed failure behind it and no designed, stated operating condition naming it.
