A direct-API backend: SDK synthesis without an agent CLI — natively structured output, so it passes the backend membership criterion. Confronted triggers, any of which scheduling for work adopts this item: the codex backend has no native cost cap (a configured `max_budget_usd` is reported as not applied on a codex run, since codex can't honor it), where a direct API loop enforces the cap by construction; CI installing a full agent CLI for one headless audit; and build-verb's named escalation (arc owning its own agent loop), which would need a first-class API connection of its own. The shape: the Anthropic Messages API first — the claude backend's own provider, whose constrained-decoding structured-output guarantee arc already relies on and whose auth is the same `ANTHROPIC_API_KEY` path, so no new credential model; one-shot structured synthesis, not an agent loop, so the execution boundary is strictly tighter than the CLI backends (one request, no tools, no filesystem). The hard cap is enforced *before* the request, not metered after, and rests only on an authoritative input count: the provider's own token-count endpoint (Anthropic's `count_tokens`). arc's existing 4:1 character estimate is display-only and can under-count, so it is explicitly *not* the cap's basis — if the count endpoint is unavailable the cap can't be guaranteed and the backend says so rather than trusting an approximation. Output is bounded by the API's `max_tokens` ceiling; the request's worst-case *token* spend (counted input + `max_tokens`) is bounded exactly before the call — that token bound is the native, by-construction guarantee the codex backend can't give. The dollar figure is that exact token bound priced by the table below, so the cap is exact in tokens and best-effort in dollars: a table lagging the provider's live rates can misprice, which is why its staleness is made visible (below) rather than claimed away. A call whose priced worst case exceeds `max_budget_usd` is refused rather than sent. The per-model input/output rates are the backend's own: this backend introduces a small published-pricing table, the one place those rates live, since a pre-request cap needs rates known before the call. The table carries its provenance — the provider's published pricing page URL and a fetch date per entry — and is re-verified against that page at each release, the refresh cadence an empirical constant owes; every run's report prints the rates and their date beside the cap, so a stale table is visible exactly where it would mislead. `max_tokens` is a per-run ceiling derived from the budget, not guessed: the input cost is fixed once counted, so the cap spends the remaining budget on the largest `max_tokens` it affords; it refuses outright only when no usable output ceiling is affordable — when the input cost plus the output cost of a floor `max_tokens` (a configured minimum, defaulting to the smallest completion worth spending on, e.g. 256 tokens) already exceeds `max_budget_usd`. Acceptance: a registry row behind the same `Backend` trait, provider-guaranteed structured output, the token budget bounded natively (dollars best-effort via the disclosed table), that boundary reported like every run's.
