The installable arc GitHub App — the zero-workflow-file rung: an App identity that posts audit verdicts as rich check runs (the Checks REST API is available only to GitHub Apps, and Apps run on infrastructure the developer provides — both verified 2026-08-25: <https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app>), installed per org or repo with fine-grained permissions (on the order of checks:write, contents:read, pull_requests:read), org-level enablement as the unbypassable posture — the strongest form of the opt-in-then-firm principle github-check-gate states. Exemplars span the space: the Claude Code Action holds the Action-only shape (github-action's rung), OpenAI's Codex Connector the App shape (a hosted service behind webhooks), and semgrep the whole ladder at once — CI action, hosted app posting checks, a rules registry behind both — the structural twin of arc + rulespace. The hosted half is rulespace's (its cloud receives the webhooks, runs or brokers the audit, and feeds firing data into the registry's aggregation); arclite's side is the App's design: identity, permission and manifest shape, what a check run renders (public output inherits public-run-record's projection), and a registration held unpublished until the endpoint is real. Sits ahead of rulespace-registry in the order because the arc-side design needs nothing from the endpoint; where the two meet, rulespace-registry's one-way conformance holds — the App adapts to the registry once its base form is live, never the reverse.
