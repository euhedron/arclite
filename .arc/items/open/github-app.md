The **arc-side design** of an installable GitHub App — explicitly *not* the running App, which can't exist until rulespace supplies the hosted endpoint (later in the order). The App itself would post audit verdicts as rich check runs (the Checks REST API is available only to GitHub Apps, and Apps run on infrastructure the developer provides — both verified 2026-08-25: <https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app>), installed per org or repo with fine-grained permissions (on the order of checks:write, contents:read, pull_requests:read), org-level enablement as the unbypassable posture — the strongest form of the opt-in-then-firm principle github-check-gate states. That hosted half is rulespace's (its cloud receives the webhooks, runs or brokers the audit, and feeds firing data into the registry's aggregation). This item delivers only arclite's side and completes at a concrete, tracked artifact: a committed **GitHub App manifest** (GitHub's app-manifest format — the App's identity, the fine-grained permissions and the events it subscribes to, as a file in the repo), alongside the design of what a check run renders (public output inherits public-run-record's projection). "Complete" is that manifest and design present in the repo, registration-ready but not submitted — held unpublished until the endpoint is real, so the artifact exists and is reviewable without a live App. It sits ahead of rulespace-registry because that design needs nothing from the endpoint; the live App is rulespace-registry's to switch on, adapting to the registry once live (its one-way conformance, never the reverse).
