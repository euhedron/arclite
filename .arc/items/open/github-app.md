The **arc-side design** of an installable GitHub App — explicitly *not* the running App, which can't exist until rulespace supplies the hosted endpoint (later in the order). The App itself would post audit verdicts as rich check runs (the Checks REST API is available only to GitHub Apps, and Apps run on infrastructure the developer provides — both verified 2026-08-25: <https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app>), installed per org or repo with fine-grained permissions (on the order of checks:write, contents:read, pull_requests:read), org-level enablement as the unbypassable posture — the strongest form of the opt-in-then-firm principle github-check-gate states. That hosted half is rulespace's (its cloud receives the webhooks, runs or brokers the audit, and feeds firing data into the registry's aggregation). This item delivers only arclite's side and completes there: the App's design — identity, permission and manifest shape, what a check run renders (public output inherits public-run-record's projection) — plus a registration authored but held unpublished until the endpoint is real. It sits ahead of rulespace-registry because that design needs nothing from the endpoint; the live App is rulespace-registry's to switch on once its base form exists. where the two meet, rulespace-registry's one-way conformance holds — the App adapts to the registry once its base form is live, never the reverse.
