What the gate runs is configuration, not shell: settings declare the gate's steps — audit, align, the advisories, the meta-audits, each on or off with built-in defaults — read by an `arc gate` command the hook shells out to, so `.arc/hooks/pre-push` collapses to a one-line shim and gate composition is set like any setting (CLI and TUI), never by editing bash. The shape, following the taxonomy/ruleset settings pattern: a `gate` settings key holding an ordered list of steps, each `{verb, blocking, <per-run options>}` — the per-run options being the same invocation parameters the command already takes (backend, ruleset, include/changed, fail-on-findings), named by their existing settings/flag names so the step is just a declared invocation, not a second parameter language; list order is run order; blocking marks whether a step's findings fail the push (audit/align blocking today, the advisories not). The built-in default list reproduces the current hook's sequence, so an unconfigured repo gates exactly as the shipped hook does. The no-parallel-config principle is honored at its actual boundary — duplication: the configured steps are the composition's single home, read by `arc gate` and restated nowhere (the shim names no verbs, so there is no second statement to rot — the ruleset pattern applied to the gate), and the full shell hook remains available to anyone wanting shell-level control (the configured gate is the default posture, not a cage). The same configured gate definition is then what CI invokes, so the local hook and the CI check can't drift. A step's trigger *scope* is not defined here — it is gate-change-scope's later addition to this step config; a step configured before that lands simply always triggers.
