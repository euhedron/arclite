Deconstruct the project's specification into modular parts — facets: the project described as data rather than one prose mass, facets composing sub-facets where scope calls for it, organized by a thin configuration in order.json's spirit (the arranger: `shape.json`, described below) — so reorganizing is a config edit rather than a prose rewrite, and the README (or any view of the project) is an assembled rendering of the parts. A project should be fully describable via its specification, and "facet" names an abstract shape whether or not it is built yet, and subsumes the README's earlier facts-as-third-concept question — a facet describes, where "fact" implied authority. Typed facets admit a dedicated spec audit — its own vocabulary beside align and rule-quality, every artifact class carrying its own quality gate. Per-facet changed-versus-unchanged becomes visible; the whole seeds by extraction from the existing README and codebase, the way rules are extracted — never a big-bang rewrite. The shape: facets are **flat Markdown files in one folder** — shipped default `.arc/spec/`, the folder settings-overridable like every configured path — with **`shape.json` as the arranger**: a tree of group nodes, each `{title, description?, ordered?, closed?, children}` where a child is either another group node or a facet reference (a leaf naming a facet file's stem, no extension, resolved against the spec folder) — so grouping, section descriptions, and nesting are the tree's own structure (never directories), and ordering/closedness are the per-node booleans; `order.json` is the degenerate case, one closed-ordered group whose children are all leaves. Prose in Markdown, arrangement in JSON — the items model generalized (order.json is a degenerate shape.json: one ordered, closed, total list). List semantics ride explicit booleans, each defaulting to the weakest claim, since a JSON array is always serially ordered and intent must be declared: `ordered` (sequence-drift is auditable only where order was chosen) and `closed` (complete enumeration versus illustrative). Facets carry descriptions, never maturity metadata: an unfinished part is described to the specificity currently supported. The spec audit is a verb, **`orient`** — a registry row today with its taxonomy settings-configurable from day one, and a pure configuration once verbs-as-configurations lands its remaining steps. The audit's vocabulary is a drift/coherence taxonomy over the facets — contradiction, staleness, gap, disorder — the same shape `align` applies to items (facets audited against each other and the code; the lexicon is optional grounds consulted where one exists, never a hard prerequisite — so this item does not wait on lexicon, which sits far later in the order), not facet *meta-rules*; whether a facet is well-formed is `rule-quality`'s kind of job and comes later, if it earns a place, exactly as the rule meta-audit did for rules. The first extraction target is the two per-folder ledger READMEs (`.arc/items/README.md`, `.arc/findings/README.md`): each is really doctrine an agent session loads (the agenda contract, the findings provenance rules) that belongs in the one specification rather than scattered as folder files, and extracting them proves the facet model on real, self-contained content before the main README is touched — with the seeded-README-on-first-use behavior in other repos re-examined on the same ground once that lands.
