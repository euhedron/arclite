The closed-loop cockpit's missing piece, promoted to the head of the agenda: a `build` verb — `arc run build --item <id>` — that has the selected backend agent implement one agenda item in a git worktree scoped to that item, so implementing an item is a command, not a conversation. The context is assembled by arc and therefore consistent for every build: the src surface (the same include set the gate audits), the item's own text, and the active rules — never whatever a conversational session happens to be holding. The output is a scoped changeset in the worktree, never the launch working tree; it reaches the repo only through the standing gate — the worktree's branch is pushed and audit/align fire exactly as for any push, no parallel gate plumbing (the CLI is the composition surface). The run record carries the worktree path, the changeset summary, and the item id, so `promote`/`usage`/the cockpit read builds like any run; a merged build resolves its item with the run id in the resolution note. The execution boundary is a new, deliberately disclosed profile: today's synthesis runs confine tools to a fresh empty dir, while build grants write to the item's worktree and only it — reported in the boundary decomposition like every grant, never a silent loosening. Doctrine once it works: everything built goes through this flow — arc-built, arc-audited — with conversational sessions the exception (bootstrap, and building this verb itself); the operator's directive supersedes the earlier staged trust ladder's propose-first stage, and the benchmark question ("what we'd have done, or better?") is answered by reviewing gated changesets rather than gating adoption. If driving the external CLIs proves limiting here — context control, in-loop hooks, turn-level auditing, flagging a violation as it happens — owning the agent loop (arc's own agent with its own transcript store, hooks, and MCP/tool configuration, Codex CLI the open-source exemplar) is the named escalation, not the start.
