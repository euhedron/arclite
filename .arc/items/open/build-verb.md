A `build` verb — `arc run build --item <id>`: the selected backend agent implements one open agenda item inside a worktree arc creates for the run — a fresh branch named for the item (`arc/build/<id>`), based on the local head of the default branch — the branch `origin/HEAD` *names* (e.g. `main`), falling back to a local `main` when unset; the base is that local branch's head, not the remote-tracking tip, and the resolved branch name and sha are recorded on the run so a local-vs-remote divergence is visible rather than silently chosen. If no default branch resolves at all (no `origin/HEAD` and no local `main`), the build errors before creating anything — a worktree can't be based on a branch that doesn't exist, and guessing one is worse than refusing. Checked out under arc's run area. The agent is write-granted that worktree and nothing else — a new execution-boundary profile, disclosed in the boundary decomposition like every grant. The agent works in the worktree with read access to the whole checkout — a build *implements*, it does not synthesize a bounded judgment, so it is not scope-limited to `src` the way a gate step is, and needs no item-level scope concept (nothing borrowed from gate-change-scope, whose step-scope is a different thing). What arc assembles deliberately is the *prompt*: the item's own text, the active rules, and the repository's orienting docs (README/specification), consistent for every build. The changeset the agent writes is what the standing gate scopes and audits at push — scoping lives there, once, not duplicated here. The run ends with the changeset committed on the item branch; arc never touches the launch working tree and never pushes — the operator reviews the branch and pushes it through the standing pre-push gate like any change, no parallel gate plumbing. The run record carries the branch, the worktree path, the changeset summary, and the item id; the lifecycle beyond the run is one deterministic command surface — `arc builds` lists each build worktree with its state, derived, never stamped: *in flight* (a live run marker), *interrupted* (an errored record with the worktree still present), *merged* (the branch tip reachable from the default branch's head), else *pending review*; `arc builds --discard <id>` removes a worktree and its branch, `arc builds --resume <id>` relaunches against the same item from the worktree's current on-disk state (its working tree and last commit, not the original base — resume continues the interrupted work, it doesn't restart it), and refuses while that build's run marker is still live so a running agent is never double-driven, and a *merged* build is what `--clean` removes and what resolves the item, the run id in the resolution note. One build worktree exists per item at a time: `arc run build --item <id>` refuses when `arc/build/<id>` is already present — pointing at `arc builds` to resume or discard it — rather than clobbering in-progress work; a build started after a prior one is merged or discarded begins fresh, while the ledger keeps every historical build run for the item by run id, so re-builds accumulate as run history, never as colliding worktrees. The operator's directive: items are built through this flow, conversational sessions the bootstrap exception; if driving the external CLIs limits it — context control, in-loop auditing — arc owning its own agent loop is the escalation, whose enabling backend connection is direct-api-backend's territory.
