The rulespace registry — deliberately one coarse item, because it is a pointer: the registry (accounts, organizations, publishing and sharing, aggregated firing data — curation pressure compounding across users and orgs instead of one machine; the aggregation and arc-in-Actions boundaries with public-run-record and the github items are drawn on those items) is its own Euhedron product and repo, and its decomposition belongs to that repo's agenda, not arclite's. Residence doctrine, settled: rules live where they are used — the repo stays the source of truth for the rules it owns (the pack principle: audited where they live) — and the registry is distribution and aggregation, never residence. Publishing is a content-hash-addressed projection with lineage, so repo-versus-published drift is detectable signal rather than conflict; consuming is new ruleset source forms — a pinned git/GitHub ref (`github:owner/repo/path@rev`, the zero-infrastructure remote source standing on existing git auth and trust) and a registry ref (`rulespace:owner/pack@hash`) beside it — both resolved and cached locally, composing with local sources like any other. The core local loop never requires the registry — fully-local operation with registry-and-local composition is the field norm (semgrep, verified 2026-08-25: <https://docs.semgrep.dev/running-rules>) — while registry-backed features (accounts, credits, auditing a GitHub repo from the web surface, whatever else the registry grows) naturally require what they are: operators will use arc through different configurations for similar value, and the registry earns adoption on discovery, aggregated firing data, and trust, not on being the only pipe. What is arclite's, as the registry lands: the arc-side integrations — euhedron login beside the provider API keys, the feedback channel's outbound transport (the captured `~/.arc/feedback.jsonl` queue is its client-side buffer), the remote source forms above, and the App's hosted endpoint (the arc-side App design is github-app's item). Its open design questions — rule provenance/lineage across versions, trust and moderation of shared rules — travel with it.
