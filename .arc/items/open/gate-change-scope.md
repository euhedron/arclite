The gate becomes change-aware: a push whose changed paths fall entirely outside a step's declared scope skips that step — skipped loudly, naming the scope that excused it, never silently. The default trigger scope is the step's *effective context surface* — for audit, every repo path whose content enters the run: the `--include` set, the auto-context baseline (README and detected manifests, unless `--no-scan` drops them), the active rules' in-repo sources, and the repo's settings layer; for align, the items ledger. The target-wide git path-state snapshot stays out of the trigger scope — it carries names, not contents, and counting it would make every change a trigger — so a change touching only unread files spends nothing (exhibited live: the portfolio-manifest push — a root JSON file that is no detected build manifest and enters no step's context — bought a full gate round and a CI audit); an explicit gate-ignore list covers paths that never warrant gating. Both are settings, composing with gate-configuration's step declarations (a step's scope serves both what it reads and what triggers it), and CI reads the same declaration — a scope-skipped required check reports satisfied, not absent. The changed set is deterministic, per pushed ref from the pre-push hook's own stdin contract (`<local-ref> <local-sha> <remote-ref> <remote-sha>` lines): the range is `remote-sha..local-sha`; a deleted ref (zero local sha) triggers nothing; a ref new to the remote (zero remote sha) has no range and falls back to the step's full scope; multiple pushed refs union their changed sets.
