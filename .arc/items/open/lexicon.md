A lexicon — essentially a glossary: the project's core concepts and terms with their preferred forms, definitions, and descriptions, so language drift is caught rather than hand-policed and judgment consults the project's vocabulary as declared grounds. Like facets but one level up: high-level and implementation-independent — where facets describe the project, the lexicon establishes the meaning of the words the describing (and all judgment over the project) is conducted in — background context ensuring reasoning stands on a common language and that the vocabulary used in content and code stays restricted and consistent. The shape, following the rules and facets substrate: flat Markdown entries in one folder — shipped default `.arc/lexicon/`, the folder settings-overridable like every configured path — one term per file, filename stem the canonical form, body the definition and description. It is not a ruleset — names and meanings are grounds a judgment consults, not general principles — and it needs no separate validator: it enters synthesis as a declared, reported context source (opt-in, the auto-context-depth question's lever), and drift is caught by judgment consulting it, the same way rules and taxonomies ground a run. It is its own class under the classes-by-role doctrine (distinct from facets, which describe the project; the lexicon fixes the meaning of the words that describing is done in), with the sibling context engines' term/entity substrate (commissure, crux) the working exemplar.
