Project a repo's run record into the repo — the shape from the public-record design discussion (the README's open question keeps only the residue). `.arc/record/` as a derived render off the authoritative private ledger: written by an explicit `arc sync`, never in the run hot path; idempotent by run id; an allowlist of fields only — id, timestamp, arc version, verb, backend and model, rules and taxonomy as (id, hash) pairs, gate verdict and the gate outcome in the run state's full vocabulary (ungated, passed, blocked, errored — an errored run never reads as passed), the structured findings and note, commit anchor, and a `format` version — never prompts or other-repo traces. The field allowlist alone can't keep absolute paths out, since a finding's own text can carry one (an audit `location`, a cited path); so projection runs a normalization pass over every emitted string value that rewrites any path under the repo root to a repo-relative form and drops a record whose findings still carry an unrelatable absolute path after that — the allowlist bounds *which* fields emit, the normalization bounds *what* their content may contain, and neither alone is trusted to keep the guarantee. Cost and token usage join the tracked record only under an opt-in setting — publishing spend is a choice. (Ledger ingest is not this projection's job — that mechanism is github-check-gate's, drawn there.) Off by default everywhere; arclite opts in as the dogfood and the operator judges the actual emitted record. The same projected lines are also a serverless team-aggregation substrate — scope boundary: aggregation for a repo's own collaborators via its clones; aggregation beyond one repo's team (across repos, users, orgs) is rulespace-registry's.
