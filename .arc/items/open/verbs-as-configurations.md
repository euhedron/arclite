Finish making a verb a configuration: its role directive, taxonomy, item schema, and gate field shipped as built-in defaults a project can override — each by the override model its *kind* already uses, not a single uniform "settings" mechanism. Two models are in play and must not be conflated: the taxonomy is pure settings data, overridden at runtime with no rebuild (it already works this way); the role is prose, and dedicated-prompts makes it a built-in Markdown asset embedded at build exactly as `.arc/rules` are — so changing the *shipped default* is a rebuild, while a *project* overrides with its own role asset composed over the builtin (the builtin-plus-local pattern rules already have), no rebuild. So "overridable" here means project-overridable by that composition, never that an embedded default mutates at runtime. Today only the taxonomy is settings-configurable; the role lives as a data string on the Rust registry row (data, not phrasing hidden in code, but neither Markdown nor project-overridable yet), and the item schema and gate field are still compiled in. The role-directive-to-Markdown step — and its prompt-quality meta-ruleset — is owned by dedicated-prompts, which precedes this item; here, in order: the item schema, then the gate field, as settings data beside the taxonomy. This item's completion is bounded to exactly that: a verb's *definition* — role, taxonomy, item schema, gate field — is configuration rather than code. It does **not** claim rebuild-free *new verbs* as its end state; that is a further, separate goal, because it additionally needs verb *membership* to stop being compiled (the CLI parse, the registry, the policy map, and settings' verb-name validation all enumerate verbs at compile time today, so a genuinely rebuild-free new verb needs a registered-verbs source those surfaces read — out of scope here, a distinct later item this one is merely groundwork toward). Defining a verb as data and registering a new verb without a rebuild are two milestones; this item is only the first.
