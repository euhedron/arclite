Package the gate as a reusable composite Action in its own public repo — `euhedron/arc-action` (name and creation timing are the operator's call) — extracting the audit-gate workflow's steps verbatim: install a pinned, checksum-verified arc from Releases, provision the pinned backend CLI, run the audit with the consumer's key and an explicit backend, upload the ledger-native run record. Marketplace listing requires a single `action.yml` at the root of a public repo containing no workflow files, a unique name, and publication via a release (verified 2026-08-25: <https://docs.github.com/en/actions/how-tos/create-and-publish-actions/publish-in-github-marketplace>) — which is why this is structurally a separate repo, not a corner of arclite. The field exemplar is `anthropics/claude-code-action` (its action.yml read 2026-08-25): a composite action that installs a runtime (Bun) and runs its CLI on the runner — so runner-side provisioning is normal practice — while also offering direct-API auth, the same tension arc holds: provisioning weight on the runner is the confronted need that would activate the parked direct-api-backend if the weight proves real. Rich check annotations are out of scope at this rung — the Checks API is GitHub-App-only (github-app's rung); the workflow job's pass/fail and step summary carry the verdict. arclite's own audit-gate workflow becomes the Action's first consumer, so the packaging is dogfooded by the gate it packages. (Scope boundary: hosted and installable surfaces are github-app's; this rung has no infrastructure beyond the repo.)
