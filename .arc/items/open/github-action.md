Package the gate as a reusable composite Action in its own public repo — `euhedron/arc-action` (name and creation timing are the operator's call) — extracting the audit-gate workflow's steps as they stand at extraction time: install a pinned, checksum-verified arc from Releases, provision the pinned backend CLI, run the audit with the consumer's key and an explicit backend, upload the ledger-native run record. (Ship-then-generalize, deliberately: this item depends on nothing from gate-configuration and is correctly ordered ahead of it — it packages the current shell invocation, which exists today, and when gate-configuration later lands the workflow and the Action both re-route their invocation through the one configured `arc gate`, by that item's own can't-drift clause; the Action's packaging survives, only the command inside it collapses.) Marketplace listing requires a single `action.yml` at the root of a public repo containing no workflow files, a unique name, and publication via a release (verified 2026-08-25: <https://docs.github.com/en/actions/how-tos/create-and-publish-actions/publish-in-github-marketplace>) — which is why this is structurally a separate repo, not a corner of arclite. Runner-side provisioning weight, if real use proves it heavy, is a confronted trigger for direct-api-backend. Rich check annotations are out of scope at this rung — the Checks API is GitHub-App-only (github-app's rung); the workflow job's pass/fail and step summary carry the verdict. arclite's own audit-gate workflow becomes the Action's first consumer, so the packaging is dogfooded by the gate it packages.
