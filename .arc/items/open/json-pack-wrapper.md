Accept a `{"rules": [...]}` wrapper object beside the bare list in the JSON rule-pack reader, ignoring unknown sibling keys — a pack file's metadata (name, version, provenance) stays the publisher's concern; arc reads the rules and nothing else. The rulespace registry serves packs as wrapper objects (its session proposed this as their item 840, 2026-08-21), and sibling systems' canonical rulebooks tend toward the same shape, so accepting both means a registry-published or sibling-owned pack is an arc source verbatim — no transformation step to write or to drift — while the bare-list form stays valid and nothing existing changes meaning. (Scope boundary: a reader affordance, not a schema commitment — arc does not define or validate the wrapper's metadata keys and gains no dependency on the registry's format evolving; if the two ever need a real shared pack contract, that question belongs to rulespace-registry.)
