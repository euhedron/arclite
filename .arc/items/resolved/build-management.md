Manage the worktrees `build` produces — build-verb precedes this and produces them; this is the surface for their lifetime. `arc builds` lists each build worktree with its state, derived never stamped: *in flight* (a live run marker), *merged* (the branch tip reachable from the default branch's head), *pending review* (the item's latest run record carries `outcome: completed` with the committed sha — build-verb's clean-completion field, a field on the run record itself, not a separate artifact), else *interrupted* (no such record — an errored run carries `outcome: errored`, a hard kill left no final record at all, and both mean the build did not cleanly finish). State reports the *latest run's outcome* for the item's one worktree — a fact about that run's record, deliberately not a live diff of the worktree (once a run completes, the worktree is the operator's to review and amend before pushing; those amendments are their review in progress, not a new state, so `arc builds` reports what the last run did, not whether the tree has since been touched). The signals are read in priority order: a live marker, then branch-tip reachability from the default branch, then that latest run's `outcome`. Earlier runs for the item are ledger history, never state inputs, so a prior clean completion doesn't make an interrupted re-run read as pending-review. The signals are independent, so every worktree lands in exactly one state: an errored run (outcome errored, unmerged) falls through to *interrupted*, never between states. The commands key on the item id — one live build worktree per item, so the item id names it unambiguously; per-run build ids are ledger history, not worktree handles. `arc builds --resume <item>` applies only to an *interrupted* worktree — it relaunches against the same item from the worktree's current on-disk state (its working tree and last commit — continuing the interrupted work, not restarting from base); it refuses an in-flight one (a live marker — a running agent is never double-driven) and a merged or pending-review one (nothing to resume — discard or review it instead); `arc builds --discard <item>` removes a worktree and its branch; a *merged* build is what `--clean` removes and what resolves the item, the run id in the resolution note. `arc run build` refuses a second worktree for an item that already has one — pointing here to resume or discard it — so re-builds accumulate as ledger run history, never colliding worktrees.
