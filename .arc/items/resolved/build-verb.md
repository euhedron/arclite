A `build` verb — `arc run build --item <id>`: the selected backend agent implements one open agenda item inside a worktree arc creates for the run — a fresh branch `arc/build/<id>` based on the local head of the default branch (the branch `origin/HEAD` names, falling back to a local `main`; the base is that local branch's head, not the remote-tracking tip, recorded on the run so a local-vs-remote divergence is visible, and the build errors before creating anything when no such branch resolves). This is a distinct execution path from the synthesis verbs, and the item's first build: the synthesis backends run the agent CLI *constrained* — structured output, tools and filesystem denied — because they want a typed judgment, not actions; build instead drives the same CLI in its native *agentic* mode, tools and edit/commit enabled, write-granted that worktree and nothing else (a new execution-boundary profile, disclosed in the boundary decomposition like every grant), read access to the whole checkout. So build is not a structured-result run: its product is the committed changeset in the worktree, not a `results` payload — a second invocation shape behind the `Backend` trait (an `implement` alongside `synthesize`), the agentic counterpart to the constrained synthesis path, which this item adds. What arc assembles deliberately is the *prompt*: the item's own text, the active rules, and the repository's orienting docs (README/specification); that prompt is this verb's, inline like every verb's — and dedicated-prompts migrates *all* verb prompts to Markdown in one pass, so build's is just one more in that set, not a build-specific migration or avoidable rework (the alternative, waiting for dedicated-prompts first only to author build's prompt as Markdown, would reorder the operator's priority for no saved work). The run ends by committing the agent's work on the item branch and marking the run record *completed* — the clean-completion signal is a field on the run's own ledger record (`outcome: completed`, carrying the committed changeset's sha), not a separate artifact, so it is written in the same final ledger append that closes the run and is tied to the commit by that recorded sha; a run that produces no change or cannot commit closes with `outcome: errored` (naming which) instead, never `completed`, so build-management reads it as interrupted, never pending-review. The build runs no verification of its own — correctness is the standing pre-push gate's job when the operator pushes the branch (the same gate every change faces), so build owns "did the agent produce a committed change," never "is the change good." arc never touches the launch working tree and never pushes — the operator reviews the branch and pushes it through the standing pre-push gate like any change, no parallel gate plumbing — and the run record carries the branch, the worktree path, the changeset summary, and the item id. Managing those worktrees over their lifetime (listing, state, resume, discard, cleanup, item resolution) is build-management's, the next item. The operator's directive: items are built through this flow, conversational sessions the bootstrap exception; if driving the external CLIs proves limiting — context control, in-loop auditing — arc owning its own agent loop is the escalation, reached only once that limitation is demonstrated in use; its enabling backend connection is direct-api-backend's, which sits later in the order.
