# arclite

> *Nothing is canon. Everything can evolve.*
>
> **NOTE**: An experimental project under rapid development — treat any part of any file, and any architectural/formatting/structural decision, as in-progress, not settled (expect unfinished, abandoned, or sub-optimal thoughts).

## Overview

arclite is an **agent-first, cross-platform CLI for AI-powered cross-repo code intelligence and auditing** — model judgment grounded, constrained, and made observable through deterministic repository inspection. It gathers facts **deterministically**, and applies **AI** at the judgment step (via an agent CLI — Claude Code or Codex, selectable per run). Every use is cost-transparent, configurable, and observable (see [Principles](#principles)). The aim: unlock analysis/auditing that doesn't already exist, while spending *sensibly*.

Open source (MIT), built by [Euhedron](https://euhedron.com) — shipped as **Arc**, from this repo (`euhedron/arclite`). This repo is also arclite's own proving ground: every push is gated by its own audit, and `.arc/findings/` is the live ledger of what those audits caught — the commit history *is* the product demo. And the proving ground is wider than this repo: arc audits a growing set of Euhedron initiatives (most not yet public, some carrying competing audit systems of their own) in the name of generating cross-repo signal.

## Getting started

**Prerequisites.** The downloaded binary is self-contained — **no Rust needed to run it** (a Rust toolchain is only for the *from-source* build below: `cargo`, with Rust as new as the crate's `rust-version`, for let-chains). arc's AI commands are powered by an **agent CLI on your `PATH`** — [Claude Code](https://code.claude.com/docs) (`claude`) or [Codex](https://developers.openai.com/codex) (`codex`); at least one is required, and you select which — per run with `--backend`, or standing via the `backend` setting. `git` grounds synthesis prompts in path-tracking state and backs `--changed`, `arc init --hook`, `arc update`, and per-run commit provenance; `curl` is only for `arc update --apply` and the provider model listings (`arc models`, the TUI's model pickers). The deterministic commands (`inspect`, `doctor`, `status`, …) need none of these. The execution boundary below is audited against Claude Code 2.1.216 and Codex CLI 0.144.4; an older CLI that does not recognize a required flag/config key fails the run instead of silently weakening it. `arc doctor` reports what's installed.

**Install.** Every channel below installs the same per-OS binary the release workflow publishes to the repo's **[Releases](https://github.com/euhedron/arclite/releases)** (macOS arm64/x86_64, Linux x86_64/arm64, Windows x86_64) — no clone, no Rust; pick one and finish with `arc doctor`:

*Homebrew* (macOS & Linux):

```sh
brew install euhedron/arc/arc
```

*Install script* (macOS & Linux — installs to `~/.local/bin`; `ARC_INSTALL_DIR` overrides, `sh -s <version>` pins):

```sh
curl -fsSL https://raw.githubusercontent.com/euhedron/arclite/main/install.sh | sh
```

*Install script* (Windows PowerShell):

```powershell
irm https://raw.githubusercontent.com/euhedron/arclite/main/install.ps1 | iex
```

*Direct download*: grab `arc-v<version>-<os>-<arch>` from Releases, put it on your `PATH` as `arc` (`arc.exe` on Windows; `chmod +x` on Linux/macOS).

*From source* (to develop arclite):

```sh
git clone https://github.com/euhedron/arclite.git && cd arclite
cargo install --path .        # installs the `arc` command; or `cargo build --release` → target/release/arc
```

**Updating**: `arc update` checks the latest release on every channel; `arc update --apply` self-replaces script and manual installs, and a Homebrew install is detected and pointed at `brew upgrade euhedron/arc/arc` instead — the keg belongs to brew. Each release from v0.1.12 publishes a `SHA256SUMS` beside its binaries; the install scripts verify against it automatically (same-channel checksums — corruption defense sharing the release's trust root, not an independent one: see the update-integrity note under the Roadmap's release item).

**Use** — common commands (a `<repo>` argument defaults to `.`):

```sh
arc                                  # no args → help (the binary is `arc`; the project is arclite)
arc inspect <repo>
arc doctor
arc update
arc status
arc tui
arc log [<id>]
arc usage
arc rules
arc items [--id <id>]
arc models
arc feedback "found a rough edge" --issue
arc feedback "queue this thought for the next session" --inbox
arc config set backend <name>
arc init <repo> --hook
arc run summarize <repo>
arc run suggest   <repo> --include src
arc run audit     <repo> --include src --ruleset <id>
arc run critique  <repo> --backend codex
arc run extract   <repo> --runs 3
arc run evolve    <repo> --ranked
arc run verify    <repo> --changed
arc run align     <repo>
arc promote <run-id>
arc retire  <verify-run-id>
```

Run `arc <command> --help` for what a command does and its full options — authoritative there, not restated here where the copy would rot. The AI commands share one option surface (select the rules, shape the context, choose the model/tools/backend, bound or preview the spend, control output and the **gate**). Every run echoes the exact parameters it used — model, Arc-requested tool grants, the decomposed execution boundary (including residual provider-managed inputs), the full list of **context sources**, the active `.arc/settings.json` layers, and where the run was logged — alongside real token usage + cost (codex reports tokens only — no dollar cost).

**Configuration** lives in `.arc/settings.json`, layered user (`~/.arc/`) then project (`<repo>/.arc/`): flat, domain-named top-level keys (`backend`, `claude_model`, `max_budget_usd`, …) — set by hand or with `arc config set` — plus **rulesets**, named compositions of *sources*: directories of Markdown rules, single `.md` files, or **JSON rule packs** (a `{id, statement, enabled?}` list — the shape a rule-owning system keeps as its source of truth, audited where it lives instead of mirrored into generated `.md` copies that would drift; directory walks stay `.md`-only, so a pack is always named deliberately), including shared pools. A **built-in `default` ruleset ships in the binary** — the rules arc audits itself with, embedded at build time — so `--ruleset default` (and a fresh `arc init`, which selects it) audits against real rules with zero curation; the reserved source literal `builtin` composes the shipped set into any ruleset beside local sources (`"sources": ["builtin", "rules"]`, later sources winning on id collisions), and a project defining its own `default` overrides the built-in, disclosed. Project layers over user; `--ruleset`/`--rules` override per run. The **backend is always an explicit choice** — `--backend` per run, or the `backend` setting: there is no built-in default backend (the backend is the thing that spends), so with neither set an AI command errors naming how many backend CLIs are detected and how to choose, never silently picking a vendor. arclite's own rules are its `self` ruleset, the configured default. A root-level `disabled_rules` list switches individual rules off by id — filtered out of every run and report, always disclosed, never silent (`arc config set disabled_rules a,b`, or toggle with space in the TUI's rules view). **Taxonomies** — each verb's vocabulary of findings — follow the same built-in-defaults pattern: a `taxonomies.<verb>` entry (a `{kind, description}` list) merges over the verb's shipped set by kind label — restate a label to override its description, add a new one to extend — and every run records the effective vocabulary it judged under. With a taxonomy in play, the per-item `kind` is **enum-locked to it in the run's schema** — membership is the provider's constrained-decoding guarantee, like every structured field — and `--free-kinds` is the deliberate, recorded opt-out. Provider API keys (for `arc models` and the TUI's model pickers) are user-layer only and masked in every output; the standard env vars take precedence.

**Logging** — every *real* AI run appends its parameters and ground-truth tokens + cost as a one-line JSON record — a completed run, or one that errored mid-flight after spending (either backend), so a failed run's real cost is recorded rather than lost — and stores its full result alongside: a durable trace that outlives the terminal and the substrate for "is the spend earning its keep" metrics (`arc usage` rolls it up locally; `arc log` and `arc log <id>` browse and re-show runs without re-running them). On by default (the `logging = false` setting turns it off); dry runs are never logged — no spend, nothing to record. `arc doctor` shows where.

**Gating on push** (opt-in) — a git **pre-push hook** runs arc commands as a gate: `arc run audit --fail-on-findings` exits non-zero on violations, blocking the push; a repo tracking items (`.arc/items`) gains the agenda gate (`arc run align`) the same way. arclite ships a tracked `.arc/hooks/pre-push` as a *starting point, not a canon* — read it to see the current setup, and edit it freely; a hook is configurable by definition (`arc init --hook` scaffolds a minimal one for any repo). A fresh scaffold gates against the built-in `default` ruleset — real rules from the first push; curate the repo's own ruleset (or compose `builtin` with local sources) as its standards take shape. Enable for a clone with `git config core.hooksPath .arc/hooks`; skip one push with `ARC_GATE=0 git push`; disable by unsetting `core.hooksPath`. It spends real AI tokens per push (announced, with the cost printed) — deliberately pre-*push*, not pre-commit, and opt-in, because passive per-commit AI spend is arc's failure mode.

## Background & motivation

arclite is a fresh, stripped-down **successor to** the legacy `arc` project — an early, premature seed of this same arc rather than a separate predecessor: its lessons (cautionary *and* generative) and ideas are carried forward on merit; nothing carries over by default. It is **not** meant to replace Claude Code or other tools (it can't keep up); the goal is to unlock new, efficient analysis/auditing workflows that don't already exist — *without* requiring users to understand its internals (arc was not user-friendly).

Two arc failure modes arclite must avoid:

- **Unsustainable AI spend** — arc's automations consumed usage at an unsustainable, opaque rate. arclite makes every AI use configurable, observable, and balanced.
- **Complexity outgrowing comprehension** — arc became too complex for new developers to understand or benefit from. arclite must stay intuitive as it grows.

Worth carrying over (on merit): self-derived/generated docs — users/agents shouldn't have to hand-maintain them.

## Specification

- **Platforms**: targets Windows, macOS, and Linux (built in Rust; ships as a single self-contained binary per platform).
- **CLI**: should be able to do and see anything, via flags.
- **Scope**: multi / any / cross repo — point it at any repository.
- **Rules as composable levers**: rules (coding standards, anti-patterns, principles) are reusable *levers* — not just prompts or memory — extracted from repos, curated, and composed into named **rulesets** that any command applies (their sources and scoping are covered under **Configuration**). A rule must capture a **general principle** — the larger intelligence, applicable across repos and contexts — never narrow wording aimed at one codebase's specific attribute, nor a rule adopted because it would catch something in the repo at hand; a clearly-stated principle needs no examples.
- **Auditing & linting**: check a repo against selected rules and surface drift/violations — on demand (a gate) or passively (a pre-push hook).
- **Discovery**: integrate with existing agent memory/config (Claude Code, Codex, …) — content storage and structure compatibility.
## Principles

The philosophy that defines arclite. (The *code's* own engineering standards — DRY, no hardcoding, single-source — live in `.arc/rules/` and are enforced via `audit`, not restated here.)

- **Agent-first, human-accessible** — usable by both agents and people.
- **Leverage, don't replace** existing, ever-evolving agent tools (e.g. the Claude Code CLI).
- **The CLI is the composition surface** — hooks, CI, and agents compose `arc` commands directly; don't re-encode invocations as a parallel config language that only mirrors argv and rots against it.
- **Maximally transparent, observable, and honest.**
- **Deterministic until synthesis** — gather/compute deterministically; reserve AI for the judgment step.
- **AI as scoped, advisory judgment** — model reasoning is pointed at deliberately controlled grounds — the rules, a declared taxonomy — and returns findings to factor in, not verdicts to obey: a contradiction, a duplication, a disordering, a gap. Where the reliably-agreeable line sits is not declared in advance; it emerges and stays visible in the taxonomy and rules themselves, sharpened through exercise whenever a finding misses (there is no canon to judge against — a finding names its grounds). What is guaranteed is control: nothing steering the judgment hides outside the configurable, auditable levers.
- **Sensible, observable, configurable AI spend** — no *arbitrary* defaults (the model default is configurable down for cost); preview before spending (`--dry-run`); hard-cap a run (`--max-budget-usd`, on backends with a native cap); report every run parameter alongside real token usage + cost; balance context utilization against value.
- **Every run is signal** — each AI run produces *unique* signal: either productive change, or a pointer to how the system (rules, prompts, context) should change to yield better signal next. Runs are therefore never cached or memoized to "save" spend — re-running *is* the value; sensible spend is spend that *earns* signal, not spend *minimized*.
- **Trace, resolve, evolve** — unexpected/sub-par results are signal: make them traceable, diagnose, then improve the system — including the rules and prompts themselves, which are validated and sharpened through exercise, not assumed correct.
- **Adversarial, self-accountable** — build in self-checking (arclite is exercised on itself); a gate turns that into accountability — change proceeds only once the system is balanced, with no outstanding violations. The gate tests the **rules** as much as the code: resolve a finding by fixing the code, or — when the finding itself is off — by sharpening the rule.
- **Never done — balance is a floor, not a finish.** A clean audit isn't a win to rest on; it's the balanced state that lets the next change proceed. Commands and rules are levers to fire and tune to keep the loop running; when a repo stops yielding signal, point arclite at another to surface its own weaknesses.
- **Leverage derivation/transclusion/resolution** — derive docs and content from the system rather than hand-maintaining parallel copies; reach for transclusion-style machinery only where mix-and-match flexibility genuinely earns it. Plain duplication needs no machinery — it's a defect: give each fact one home and point to it.

## Roadmap

Not a plan or a commitment; it evolves as signals warrant. What has **landed** is narrated below. What is **open** is tracked as the agenda in [`.arc/items/`](.arc/items) — one Markdown item per file, `order.json` the intended order (see its [README](.arc/items/README.md)) — audited by `arc run align` and gated on push; pointed to from here, never mirrored, so the two can't fork. (A landed item's leftover edges are noted inline below until they warrant items of their own.)

**Landed, with open edges:**

- [x] **Multi-run** — `--runs N` runs a command N times concurrently and unions the `results` (only byte-identical items collapse). The substance-merge that edge called for is now the `aggregate` verb (under **Open**). Open: sequential pass-forward (each run sees prior findings); fanning one union across *different* commands.
- [x] **Run logging + rollup** — mechanism under **Logging** above (each run stamps arc's release `version`), now with **ledger analytics**: `arc usage` is the analytics home — the spend rollup and the **per-rule firing rollup** (`--rules`) as two lenses over one dataset, `--repo` filtering either. Every run records its active rules as **(id, content-hash) pairs**, so firing attributes to the rule *version* that was in play — the current version's record split from historical ones, with runs predating the field disclosed as exposure-**unknown**, never zero (and never back-parsed from display prose). Firing is curation signal, not a verdict: the display surfaces the distribution and its outliers — the fired tail with per-version breakdowns, and the never-fired tail with exposure counts. Open: team aggregation; trends over time (audit pass-rate, cost curves).
- [x] **`arc status` + live stats** — one marker file per in-flight run, streamed with live progress (output characters, turns, tool-calls) so `arc status` and the TUI footer track it live. A marker orphaned by a hard-killed process is pruned by a pid-liveness probe (Unix `kill -0`, Windows `tasklist`) and disclosed, never reported as active; an inconclusive probe keeps it (over-reporting one dead run beats hiding a live one). Open: richer per-run detail.
- [x] **Codex backend** — `--backend codex` drives `codex exec` behind one `Backend` trait, so usage spreads across subscriptions. Default runs suppress project instructions/config/skills and user config/rules, disable ordinary extension/tool surfaces, use an ephemeral session, and confine any remaining local tools to a fresh empty run directory with no network; `--ambient-memory` deliberately reopens the target project as a read-only ambient root. The report does **not** call that total isolation: user/admin/bundled skills and managed provider policy/tools can still apply, and are disclosed. A capability a backend can't honor is rejected before spend (codex has no native cost cap; `--allow-tool` isn't yet mapped to its tool/permission model). A **Cursor backend** (`cursor-agent -p`) joined through the same trait when both API wallets ran dry in one week, then was **removed** once its structural gap surfaced: `cursor-agent` has no native structured-output mode (verified in the CLI and [its docs](https://cursor.com/docs/cli/reference/output-format) — its `json` format is a transport envelope whose `result` is free text), so its schema "contract" was prompt-carried hope. That set the backend **membership criterion**: a backend must natively enforce the verb's schema on the model's output to join the registry — provider-guaranteed structure is the load-bearing contract everything downstream (gate, log, promote, aggregate) acts on. Open: the `--allow-tool`→codex bridge.
- [x] **Git-state grounding for synthesis** — every prompt now carries a deterministic Git truth block: index/dirty state for the README, manifests, and `--include`/`--changed` files it read, plus collapsed changed, untracked, and ignored path sets for the target. The snapshot itself adds path/index metadata, not those files' contents (an explicitly included ignored file still follows normal include behavior); says a path mentioned by a tracked file is not thereby tracked or committed; and marks state unavailable on plain directories instead of letting unknown masquerade as clean. Its source summary makes the path-name disclosure and counts visible in dry runs, live output, and logs. Open: privacy/volume shaping for the default-on, target-wide, currently unbounded exception-name inventory sent to the selected backend.
- [x] **`arc tui`** — an interactive cockpit over the same commands: inline (preserves scrollback), render a pure function of state. The recurring surfaces have views (status/config/rules/log/usage/doctor); config editing and rule toggling write through the same path as `arc config set`; the launch gate previews a verb's `--dry-run` at zero spend, and shaping keys (`b`/`m`/`r` for backend/model/ruleset) re-run the preview so the shown command is exactly the one fired. The usage view is the ledger-analytics cockpit under a **repo lens** — cycling all-repos → the launch directory → every repo the ledger knows, its spend ↔ rule-firing pages arrow-navigable tabs — embodying the TUI's principle: **the launch cwd is a default lens, never a boundary**. Keys follow the cockpit bar the agent CLIs set: arrows/enter/esc carry primary navigation; letter keys are labeled accelerators, never a function's only path. One `arc tui` oversees every repo's runs (the human's surface, alongside however many agent sessions; the CLI stays the agents'). The rules view carries each rule's firing record beside the rule itself (row counts + per-version detail, this repo). Open: extending the repo lens to the remaining cwd-scoped views (rules/config resolving a *selected* repo); views for the remaining deterministic commands (inspect, update, models, promote, retire); shaping the launch's *context* (include/exclude/changed); surfacing a failed launch inline; live output streaming; and the larger aim — findings and extracted rules as interactive structured items acted on in place.
- [x] **Release pipeline + `arc update` + distribution** — public since v0.1.8, linked from [euhedron.com](https://euhedron.com): `.github/workflows/release.yml` builds per-OS binaries (five targets, Linux arm64 included) and uploads them with a `SHA256SUMS` to [Releases](https://github.com/euhedron/arclite/releases) on a version tag; `arc update` checks the latest and `--apply` self-replaces, tokenless against the public repo (a private mirror's assets take an optional `ARC_GITHUB_TOKEN`, kept off argv). **Distribution channels** (the agent-CLI pattern: install script as the front door, Homebrew beside it, releases as substrate): `install.sh`/`install.ps1` in-repo (checksum-verifying, version-pinnable), and a Homebrew **tap** — [`euhedron/homebrew-arc`](https://github.com/euhedron/homebrew-arc), a binary formula for macOS + Linux, auto-bumped by the release workflow via its `TAP_GITHUB_TOKEN` secret (absent the secret it skips with a notice; `bump.sh` in the tap is the manual path). `--apply` is channel-aware: a Homebrew-managed keg is detected by path and deferred to `brew upgrade` rather than forked from brew's records. Update integrity rests on HTTPS transport + the GitHub release's authenticity, not a bundled signature — the same-channel `SHA256SUMS` shares the release's trust root, so real tamper-resistance would need an out-of-band signing key or build attestations. A post-release verifier (`verify-release.yml`) exercises every channel — binaries checksum-verified and run, install scripts, tap, update-from-previous — on fresh per-OS runners per release. Open edges tracked as the `release-verification` item (remaining registries, signing).
- [x] **Feedback channel** — `arc feedback`: one verb, two sinks. An **outbound** report is captured to `~/.arc/feedback.jsonl` — collection first, transport later (the registry's future); `--issue` prints a prefilled GitHub issue URL as the zero-infrastructure interim, carrying the message and the running arc's identity and deliberately nothing else (a run's mechanics stay the operator's — the public-record doctrine applied). `--inbox` queues a note into the repo's `.arc/inbox/` — one Markdown file per note, README-seeded on first use — for the next session to read and triage: the agenda's lighter-weight cousin, and the operator's way to hand ideas to future sessions without a live conversation. The TUI's feedback view lists both queues and composes through the same write paths (`n` report, `i` inbox note); pending notes and agenda drift surface ambiently (`arc doctor`'s items row, the TUI masthead's launch warning). Open: the euhedron endpoint (rides the rulespace registry).
- [x] **Surface available models** — `arc models` (and the TUI's model pickers) list each backend's provider-reported models (Anthropic/OpenAI `/v1/models`), keyed by the standard env var or a masked, **user-layer-only** `api_keys.*` setting (the loader rejects a project-layer key, so a tracked settings.json can never hold a secret). Open: reconciling the compile-time model defaults against the live listing.
- [x] **Errored runs logged on both backends** — a run that fails mid-flight after spending records its real usage as a logged errored run, so the spend is traced rather than lost.
- [x] **Aggregate rules/findings across repos** — `arc run aggregate --from <run-id> …` feeds prior logged runs' structured results into context and merges the items that are the *same in substance* (the AI judges sameness; each merged item carries the `sources` it drew from, so recurrence is counted, not model-asserted, and `covered_by` flags an active rule that already expresses it). Works over any structured runs — extract candidates, audit findings. Open: promoting merged rules to shared pools; a `--repos` convenience that runs the extracts before aggregating. Extract candidates banked against the curation bar: `distinguish-unknown-from-zero`, `snapshot-referenced-state-at-record-time`/`reconcile-cached-verdict-with-live-state`, `idempotent-reingest-via-stable-keys`, `stream-unbounded-external-data`, `resolve-packaged-assets-relative-to-module`, `revalidate-gate-before-irreversible-commit`, `aggregate-from-authoritative-ledger`, `curated-list-orders-not-filters`, `group-parameters-into-a-struct`, `impose-deterministic-order-on-unordered-sources`, `feed-child-stdin-without-deadlocking`, `scaffolding-must-be-idempotent-and-nondestructive`, `reload-canonical-state-after-write`, `validate-success-by-required-artifacts`, `scope-temporary-artifacts-to-one-operation`, `revalidate-external-structured-output-before-acting`; and `ai-inference-stays-advisory-never-authoritative` (central to the sibling systems but likely too architectural for a concrete code rule). If banked/candidate tiers ever ship as selectable pools, the field's norm (clippy holding `pedantic` outside `all`; ruff's small default select) keeps them **opt-in** — the default stays the curated core.
- [x] **Built-in default rules** — `.arc/rules/` embeds into the binary at build (one source: the same files arclite audits itself with; the rules version is the binary version every log stamps), exposed as the reserved source literal `builtin` and the always-resolvable `default` ruleset — a stranger's `arc init` → `arc run audit` finds real rules immediately instead of passing vacuously. `disabled_rules` prunes per repo without forking; a project's own `default` overrides the built-in, disclosed; `builtin` composes into any ruleset beside local sources. Open: materializing *editable copies* into a repo stays deliberately unbuilt — parallel copies diverge (three sessions later, three drifting rule sets across repos); revisit only if real use outgrows disable-and-compose.
- [x] **Promote findings into the repo** — the **extract → promote → verify → retire** lifecycle is whole and system-owned: `arc promote <run-id>` writes a run's structured findings into `.arc/findings/open/` (atomic names, commit-anchored, seeding an agent-facing ledger README on first use); `arc run verify` re-checks the open ledger against current code (`reproduces` | `resolved` | `indeterminate`, each grounded in a cited mechanism); `arc retire` moves the resolved ones into `resolved/` (verify-run-only, section-scoped resolution notes). `--findings` feeds the ledger into a run to hunt past what's known. Open: cross-scope curation (repo vs. `~/.arc`); same-issue supersession on re-promote; description-based entry naming (today it takes the finding's longest field, often an identifier slug).


## Open questions

- **Rules — format & lifecycle.** A rule is a **Markdown file** (filename stem = `id`), or one entry in a **JSON rule pack** (see **Configuration** — added so sibling systems' canonical rulebooks are audited in place); rulesets compose sources. The ruleset audits *itself* for generality: a `rule-quality` ruleset of meta-rules under `.arc/meta-rules/` audits `.arc/rules` in the pre-push loop when rules change, so a curated rule can't land example-bound or tied to arclite's current state (it has caught real current-state bindings in arclite's own rules). Rules earn inclusion by recurrence across repos — `dispatch-through-one-registry`, `report-the-identity-that-ran`, and `read-structured-data-not-reparsed-prose` (the first arclite learned from the sibling products rather than itself); candidates still awaiting the bar are banked under the aggregation item above. A division the false-incident episode settled: **rules stay general principles; facts about external systems live with checkable provenance** — an official doc plus date, a verifying command, a run id. An uncited behavioral claim is a hypothesis, not a foundation: the removed re-validation layer (see **Structured output**) was justified by exactly such a claim, recorded by an agent session with nothing to check, and later sessions built on it until the run log disproved it. Banked candidate (a sharpening of `prefer-evidence-over-assumptions`, held to the curation bar): *recorded claims about external behavior must carry their provenance so any later session can re-verify*. The real-time behavioral list (under **Gating**) is the runtime counterpart — asserting external behavior without provenance is a catchable reasoning pattern. Open: frontmatter for selective inclusion (`kind`/`scope`/`tags`), added only when something filters on it; rename-stable ids; applying the meta-audit recursively; set-level redundancy/overlap checks beyond the per-rule lens.
- **Gating / hooks for any command (cost-visible).** The gate (`--fail-on-findings`) and the pre-push hook ship (see **Gating on push**). Open: **Claude Code hook events** invoking `arc` (complementary to git hooks, not a replacement); whether a pre-commit variant earns its keep; and whether a `--runs N` union on the gate's audit (more findings per round — exercised once, it surfaced a gap the single runs missed) or moving the non-blocking advisories to periodic/on-demand better balances cost against signal — twenty-plus gate rounds on this repo show a heavy push converging a-finding-or-few per round rather than exhausting in one pass, each round digging past the last (the loop's cost is real, and so far so is every round's signal). A further open direction: a **real-time counterpart to the change-gate** — a cheap, opt-in model tailing an agent's *live* session (via those hook events, or the session transcripts these CLIs already write and the sibling context engines already ingest) to catch **reasoning/behavioral** anti-patterns as they happen — a ruleset distinct from the code rules — and notify, pause, or feed the caught pattern back to the agent mid-run; the per-rule firing-rate view above is also what would keep such a behavioral list honest by exercise rather than accretion. Its seed exhibits are already accumulating from this repo's own live sessions: reflexive false-efficiency; manufactured urgency/artificial scarcity (inventing time or budget pressure, then letting it trim scope); "already"-as-justification (incumbency standing in for merit); doctrine baked into comments as if current state were policy; deferring diligence to a "future" that is just us; preservation-by-default (accommodating existing state or old data without asking whether it is antithetical to the ideal shape, for a speculative benefit no confronted need ever asked for); turn-scoped work selection (sizing scope to the reply boundary, then rhetorically handing control back — "where next?" — instead of reading the standing agenda); partial-sweep verification (a truncated or sampled inspection presented as a completed check — confident negatives from incomplete enumeration); proxy verification (reducing a gate's real output to a count or pass/fail shortcut, acting on the proxy while discarding the information the check exists to provide); and external-behavior claims recorded without checkable provenance. The exhibits now stand drafted as the `behavioral` ruleset (`.arc/behavioral-rules` — defined, selected by nothing, rule-quality-clean); adoption, and any real validation, wait on live exercise — a planted test can only show the register parses.
- **Command-kit identity.** The verbs are one prompt-differentiated substrate under `arc run <verb>`, kept distinct from the deterministic top-level commands — `suggest` (what's worth attention), `critique` (defects), `audit` (rule violations), `verify` (re-checks recorded findings), `summarize` (describes), `extract` (mines rules), `evolve` (challenges the frame), `aggregate` (merges prior runs by substance). An `aggregate` of a `critique` + `suggest` run over arclite showed them **complementary** — converging only on the single most-salient issue, otherwise each surfacing its own, with `audit` silent where the code already meets the settled bar. Watch overlap/necessity/distinctness as the kit grows; let use, not speculation, justify each verb.
- **Auto-context depth.** The default context is the detected manifests + root README; `--no-scan` drops that content baseline so source-content cost can track a diff rather than a whole-repo baseline, while retaining the target-wide Git path-state snapshot (names/metadata only, with its unbounded-name edge disclosed above). Open: whether to also pull the root `CLAUDE.md`/`AGENTS.md` as an explicit (reported) source — arc's **Discovery** goal argues for it, distinct from the agent's default-suppressed project customizations; whether a lean run should drop the README too; how wide to search for prose docs vs. a light default + explicit `--include`.
- **Rules registry & distributed evolution (rulespace).** Semgrep's registry is the counter-model to embedding: rules resolved from a remote, shared home — and that is the intended future of **shared pools**: a registry ([rulespace.ai](https://rulespace.ai) — landing live, signups open; its own Euhedron project/repo) with accounts and organizations, publishing and sharing rules/rulesets, and aggregated firing/recurrence data — so learning compounds across many users, projects, and organizations instead of one machine (our own use is the primary signal, since we keep only what proves useful; external usage is validation you can't argue against). The firing-stats lens doubles as the registry's substance: entropy-like measurement of rule-firing distributions, with curation as deliberate pressure toward convergence. Core before surfaces, each minimal and polished: the cloud registry itself, then a GitHub integration (arc in Actions/PR checks, and auditing your own — or any public — repo from a web surface), then editor extensions. Open considerations: verifiable provenance/lineage of rules across versions and forks (content-hash chains; a blockchain-style trace is one candidate), trust and moderation of shared rules, private-vs-public pool boundaries.
- **Public record — what leaves the machine, what the repo publishes.** Substantially settled by design discussion; the buildable shape is tracked as the `public-run-record` item. The doctrine: **data follows its subject** — a run's mechanics (machine paths, cross-repo identity, spend) are the operator's, global and private by default, never silently flipped; a run's *judgment about a repo* (findings, verdicts, notes, (id, hash) rule exposure, blocked/passed) is the repo's, projectable into it by a second explicit bridge beside promotion — mechanical but shape-controlled, an allowlist rendered off the authoritative private ledger, regenerable wholesale (`logging = false` opts out of that ledger, dry runs never log, persistence is best-effort — authoritative, not assumed-total). Genuinely still open: cost-exposure defaults beyond arclite itself (where published spend is the ethos made falsifiable); publication norms for repos the operator doesn't own; whether promotion needs its own pressure once projection supplies the public benefit; and the standing guard — the projection's shape must never bend to its consumers (it is regenerable, and backward-compatibility pressure on it is a bias to refuse, not a duty).
- **Verbs as configurations.** The ideal shape under exploration: a verb is not code but a **configuration** — its prompt, its taxonomy (the *vocabulary of findings*: what kinds to report, each described), its item schema, its gate field — shipped as built-in defaults and overridable/extendable through settings like everything else, so nothing steering a judgment hides in code and a new verb needn't mean a rebuild. Rules stay distinct from taxonomies by role: a taxonomy names what kinds of findings exist; rules state the standards that need explicit stating. Two steps have landed: taxonomies are settings-configurable data, and a verb's prompt reduced to a minimal **role directive** plus shared assembly (the effective taxonomy block, the context, the grounding guardrail, the output notes) — no verb-specific machinery hides in phrasing. Next: roles-as-Markdown (the rules substrate), then schema and gate as data — take each when tuning without recompiling earns it.
- **Structured output vs. tool calls.** A command's typed result comes as a final **structured-output** artifact (today's `--json-schema`/`--output-schema` → `results`+`note`), whose schema conformance is **enforced by the provider via constrained decoding** — the guarantee everything downstream (gate, log, promote, aggregate) acts on, and deliberately not re-judged locally: arc verifies only that the certified artifact *arrived intact* — a schema-requested run with no payload, or an unparseable artifact, is an errored run, and an errored run never passes a gate. (An earlier local re-validation layer rested on a mis-recorded incident; the append-only run log disproved it — 332 audits, zero mis-shaped items — and it was removed. See the provenance lesson under **Rules**.) The alternative channel — the model **calling a tool per item** — is equivalent in expressiveness *and* guarantee (both providers' strict tool mode is the same constrained decoding, opt-in: Anthropic `strict: true`, OpenAI `strict`; arc's closed, all-required schemas are already strict-shaped) and differs only in lifecycle: per-item events instead of one final artifact, so a run that dies mid-way leaves salvaged items on its errored record — richer diagnostics, never gate-relevant. A lever for when a use-case earns it; it is also the channel that could readmit a tool-capable, schema-less CLI.
- **Reclaim the `arc` name.** Largely settled by launch: the binary is `arc`, and the product ships publicly as **Arc** under Euhedron ([euhedron.com](https://euhedron.com)). The residue: formally retiring the legacy `arc` repo, and whether the crate/repo name (`arclite`) ever converges on the product name (a rename redirects, so it stays cheap to defer).
- **Settings shape.** Flattened to top-level, domain-named keys after benchmarking Claude Code, Codex, Gemini CLI, VS Code, and git: the peers keep built-in defaults in code, the file holds only the operator's overrides, and none wraps user config in a "defaults" section — that word stays reserved for the built-ins (the old schema collided with it). The `backend` key is deliberately **must-choose** (rustup-style: no built-in default, because the backend is the thing that spends; unset errors with what's detected and both ways to choose). Open, each adopted only when use earns it: an ordered backend priority/fallback among detected CLIs; a gitignored per-repo local layer (Claude Code's `settings.local.json` precedent); env-var overrides (an `ARC_BACKEND` would let a shared hook run on each contributor's own backend); codex-style profiles; a generated settings JSON schema for editor validation (gemini precedent).
- **Agent-agnostic?** (Claude Code + Codex + any.) **Distribution** — per-OS binaries on GitHub Releases (via the release workflow) and `arc update` (check + `--apply` self-replace) ship now; the still-open edges live in the Roadmap's release-pipeline item, not restated here. **CI** — GitHub Actions runs build/test/lint on Linux + macOS, with a tag-triggered release build per platform. **Dashboard / IDE / linter integration?**
